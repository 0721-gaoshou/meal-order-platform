# 本地生活点餐与优惠券平台 · 项目计划书

> 版本：v1.0 ｜ 状态：待开工 ｜ 定位：秋招/面试向个人项目，预留 AI 扩展接口

## 1. 项目定位与目标

**一句话定位**：单体架构的本地生活点餐平台，覆盖 商品 → 购物车 → 下单 → 优惠券 → 支付 → 取消/退款 → 完成 的完整交易闭环，重点打磨 并发、幂等、状态机、消息队列 四类企业级问题。

**项目目标**：

| 目标 | 说明 |
|---|---|
| 工程能力证明 | 每个难点都对应一道高频面试题，且都有"方案对比 → 定案 → 验证"完整链路 |
| 可讲故事 | 订单取消/退款补偿链路、支付回调竞态，是有真实故障故事的模块 |
| 留 AI 伏笔 | 行为埋点 + 商品标签 + 分层架构，后续可平滑加推荐/搜索/客服，不用推倒重来 |

**非目标（明确不做）**：
- 不上微服务、不做分库分表（单体 + 模块化包结构，讲清楚"什么时候才需要拆"即可）
- 不追求真实上线运营（沙箱/模拟支付即可，重点是设计不是运维）
- 不预先实现 AI 模块，只做数据预留

## 4. 核心技术难点详解（本项目的灵魂）

> 每个难点按 **问题 → 为什么难 → 方案对比 → 定案 → 怎么验证** 展开。
> 面试时按这个顺序讲，就是一段完整的故事。

### 4.1 支付回调幂等（防重复扣款）

- **问题**：支付宝回调是 at-least-once，同一笔订单会通知多次；网络抖动时甚至乱序。
- **为什么难**：如果回调处理只是"改订单状态"，重复通知会把状态改回去、库存重复回补、埋点重复记。
- **方案对比**：
  | 方案 | 做法 | 缺陷 |
  |---|---|---|
  | 查状态再更新 | 先 SELECT 判断状态，再 UPDATE | 检查与更新非原子，并发下两个回调都通过检查 |
  | **状态机 CAS + 唯一索引**（定案） | ① `pay_log` 表对 `(out_trade_no, trade_no)` 建唯一索引，插入即判重；② `UPDATE orders SET status='PAID' WHERE id=? AND status='PENDING_PAY'`，affected_rows=0 直接 ACK 成功返回 | 需要保证两步在同一本地事务内 |
- **定案细节**：
  - 回调先验签，验签失败直接拒；
  - 插流水 → CAS 改状态 → 记埋点，包在一个本地事务；
  - 主流程之外发 MQ 通知（发券、通知商家），失败不影响 ACK。
- **怎么验证**：用 Mock 网关对同一订单连续回调 10 次，断言：订单只变 PAID 一次、pay_log 只有一条、库存只扣一次。

### 4.2 订单状态机

- **问题**：订单状态流转散落在各个 Service 里，任何遗漏就是一个越权 bug（如已完成还能取消）。
- **定案**：
  ```
  PENDING_PAY(待支付) ──pay──▶ PAID(已支付/待接单) ──accept──▶ MAKING(制作中)
       │                          │                                │
       │ cancel                   │ refund                         ▼
       ▼                          ▼                             READY(待取餐) ──▶ COMPLETED
    CLOSED(已取消)            REFUNDING(退款中) ──▶ REFUNDED(已退款)
  ```
  - 状态机用**枚举 + 流转映射表**（`Map<当前状态, Set<允许目标状态>>`）集中定义，非法流转抛业务异常；
  - 所有状态变更统一走 `OrderStateMachine.transition(orderId, from, to)`，内部就是带 `WHERE status=from` 的 CAS；
  - DB 层 CAS 是最后一道防线，service 层映射表是第一道。

### 4.3 订单取消/撤回的补偿链路

- **问题**：取消不是改一个字段，是一条补偿链：**库存回补 → 优惠券返还 → 退款单生成 → 退款回调 → 埋点**。任何一环失败都会造成资损或库存虚减。
- **为什么难**：本地事务只能保证订单状态和其中一两个动作的原子性，跨资源的动作（MQ、退款）必须异步 + 可重试。
- **定案**：
  1. 本地事务内：CAS 取消状态 + 库存回补（`UPDATE sku SET stock=stock+n WHERE id=?`）+ 券返还（`UPDATE user_coupon SET status='UNUSED' WHERE id=? AND status='USED'`）；
  2. 已支付订单：同事务生成退款单（`refund_order`，状态 REFUNDING），发 MQ 异步调退款接口；
  3. 退款回调按 4.1 同样幂等处理（`refund_no` 唯一索引 + 退款单状态 CAS）；
  4. 补偿兜底：定时任务扫描"取消/退款超时未完成"的中间态单据，重试或告警。
- **怎么验证**：取消后断言库存恢复、券状态回到 UNUSED、已支付单能查到退款单且只退一次。

### 4.4 取消 vs 支付回调的并发竞态（经典题）

- **问题**：用户点"取消"和支付回调几乎同时到达。取消把状态改成 CLOSED，回调随后把状态改成 PAID → 钱收了、单没了、库存没了。
- **定案**：两个操作都走状态机 CAS，**只有一个能赢**：
  - 回调赢：取消接口发现自己 CAS 失败且状态已是 PAID，提示"订单已支付"；
  - 取消赢：回调 CAS 失败（status 已 CLOSED），但钱已实际支付 → **回调兜底逻辑自动触发全额退款**，而不是静默丢弃。
- **为什么这是好答案**：体现了"幂等 + 补偿"而非"幂等 + 拒绝"。钱到账了就必须有出口。
- **怎么验证**：Mock 网关写一个"回调延迟 N 毫秒"的开关，并发执行取消 + 回调，断言终态要么 PAID 要么 CLOSED+REFUNDED，不会出现幽灵单。

### 4.5 超时未支付自动取消（延迟队列选型）

- **方案对比**：
  | 方案 | 优点 | 缺陷 |
  |---|---|---|
  | RabbitMQ TTL + 死信队列 | 概念经典，面试好讲 | 队列统一 TTL 才不出队头阻塞；过期精度受轮询影响 |
  | RabbitMQ 延迟插件（定案·主链路） | 任意延迟、无队头阻塞，一行依赖 | 插件社区维护，非官方核心 |
  | Redis ZSet 轮询 | 无需 MQ | 持久化、多实例去重、精度都要自己扛 |
  | RocketMQ 延迟等级 | 原生 | 固定 18 档（30min 恰好有），但部署重 |
  | 定时任务扫表 | 简单 | 精度差、全表扫描，不适合主链路 |
- **定案**：**延迟插件为主 + 定时任务兜底对账**（每 5 分钟扫 `PENDING_PAY` 且超时的单，漏网之鱼补取消）。双保险的故事完整：MQ 保证时效，扫表保证不丢。
- **怎么验证**：下单后不支付，30 分钟（测试期可配 1 分钟）断言自动取消且库存回补。

### 4.6 并发下单与库存超卖

- **方案对比**：
  | 方案 | 正确性 | 吞吐 | 适用 |
  |---|---|---|---|
  | 查库存 → 判断 → 扣 | ❌ 必然超卖 | — | 反面教材 |
  | **DB 条件更新** `UPDATE sku SET stock=stock-n WHERE id=? AND stock>=n`（MVP 定案） | ✅ 原子 | 中（热点行锁竞争） | 普通下单完全够 |
  | Redis Lua 预扣 + MQ 异步落库（秒杀定案） | ✅ | 高 | 秒杀/大促 |
  | Redisson 分布式锁串行 | ✅ | 低 | 演示用，不作为主方案 |
- **定案**：**先正确再提速**。MVP 用 DB 条件更新（乐观锁思想），秒杀场景再上 Redis 预扣（Lua 原子 check-and-decrement）+ 预扣成功发 MQ 异步创建订单 + DB 兜底条件更新 + 取消时回补 Redis。**不要一上来就 Redis，讲清楚每层为什么加**。
- **怎么验证**：JMeter/wrk 500 并发抢 100 库存。断言：`订单数 == min(请求成功数, 100)`、最终 `stock >= 0`、无负库存、Redis 与 DB 库存对账一致。

### 4.7 优惠券超发与核销

- **问题**：限量 1000 张的券，并发领取可能发出 1200 张；核销时可能一张券被两个订单同时用。
- **定案**：
  - 领取三步：① 查资格（是否过期/超个人上限）② `UPDATE coupon SET remain=remain-1 WHERE id=? AND remain>0` 原子扣减 ③ 插 `user_coupon`，**(user_id, coupon_id) 唯一索引**保证一人一张——并发下唯一索引兜底，重复领直接报冲突；
  - 核销：下单事务内 `UPDATE user_coupon SET status='USED' WHERE id=? AND user_id=? AND status='UNUSED'` CAS，防止同券并发核销；
  - 取消返还：仅返还未过期的券，`status='USED' → 'UNUSED'`（过期券不返还，写明业务规则）。

### 4.8 优惠券金额分摊算法（满减券拆到多个商品）

- **问题**：满 30 减 5，订单里有 3 个商品，优惠怎么分到每个 item 上？后续单件退款时退多少优惠？
- **为什么难**：四舍五入会导致 `Σ(item优惠) ≠ 总优惠`，金额对不上就是资损级 bug。
- **定案（逐项累计法，淘宝/美团同类思路）**：
  ```
  已分摊 = 0
  对前 n-1 个商品：item_i 优惠 = round(总优惠 × 累计金额(含当前项) / 订单总额) − 已分摊
  最后一项：总优惠 − 已分摊   ← 尾差全归最后一项
  ```
  保证分摊和严格等于总优惠；部分退款按 item 上记录的分摊金额退。
- **怎么验证**：构造 30−5 分到 9.9+9.9+10.2 的单，断言三项分摊之和恰好等于 5.00。

### 4.9 缓存一致性（商品/商家详情）

- **方案对比**：
  | 方案 | 问题 |
  |---|---|
  | 先删缓存再更新 DB | 并发"读-回填"会把旧值写回缓存 |
  | 先更新 DB 再更新缓存 | 写放大 + 并发写乱序 |
  | **先更新 DB，再删缓存**（定案） | 仅存在极小概率的读旧窗口，接受最终一致 |
- **定案细节**：Cache-Aside；空值缓存（TTL 60s）防穿透；TTL 加随机抖动防雪崩；热点商品互斥回源防击穿；延迟双删作为讲点而非必做。
- **怎么验证**：更新商品后立即读，断言拿到新值或短暂旧值后收敛；压测穿透场景不打到 DB。

### 4.10 重复提交防护

- **定案**：三层防御——
  1. 前端按钮 loading 防抖（体验层）；
  2. **下单令牌**：进入结算页时发一个 Redis `SETNX` 令牌，下单时 `DEL` 成功才放行（原子性由 Redis 保证）；
  3. 兜底：客户端生成的 `request_id` 在订单表唯一索引，重复插入报冲突回滚。

### 4.11 接口幂等设计总表

| 接口 | 幂等手段 |
|---|---|
| 下单 | 请求令牌 + `request_id` 唯一索引 |
| 支付回调 | `pay_log(out_trade_no, trade_no)` 唯一索引 + 状态 CAS |
| 取消订单 | 状态机 CAS（天然幂等） |
| 退款回调 | `refund_no` 唯一索引 + 退款单状态 CAS |
| 领取优惠券 | `(user_id, coupon_id)` 唯一索引 + 余量条件扣减 |
| MQ 消费（状态变更/埋点） | 业务键唯一索引或 Redis 消费去重表 |

### 4.12 行为埋点（AI 预留的地基）

- **表**：`user_behavior(id, user_id, item_id, action, scene, created_at)`，action ∈ {EXPOSED, CLICK, ADD_CART, ORDER}。
- **定案**：AOP/拦截器采集 → Spring 事件 → `@Async` 内存缓冲 → 每 100 条或每 2 秒批量 insert（量大了换 MQ 消费者批量写）。**埋点同步会拖慢下单链路，必须异步且允许丢失**（埋点丢几条没关系，阻塞交易不行——这句话面试能加分）。
- **为什么现在做**：推荐系统的原料是行为数据，项目上线后才补录的数据是脏的。

## 5. 数据库核心表设计（关键字段概要）

> 开工第一步就是细化这四组表。这里列出**决定代码形状的关键字段和索引**。

### 5.1 订单 `orders`
- `id`(雪花ID)、`order_no`(唯一)、`user_id`、`status`(状态机枚举)、
- `total_amount`(分)、`discount_amount`(分)、`pay_amount`(分)、
- `coupon_id`、`request_id`(唯一索引·幂等)、`expire_time`(超时取消用)、`pay_time`
- 索引：`uk(order_no)`、`uk(request_id)`、`idx(user_id, status, created_at)`

### 5.2 订单明细 `order_item`
- `order_id`、`sku_id`、`spu_name/sku_spec`(下单时快照，防商品改价影响历史单)、
- `quantity`、`unit_price`(分)、`coupon_share_amount`(分·4.8 分摊结果)、
- `refund_status`

### 5.3 支付流水 `pay_log` / 退款单 `refund_order`
- `pay_log`：`out_trade_no`(唯一)、`trade_no`(与 out_trade_no 联合唯一)、`amount`、`status`、`callback_body`
- `refund_order`：`refund_no`(唯一)、`order_id`、`refund_amount`、`status`(REFUNDING→REFUNDED/FAILED)

### 5.4 商品 `spu` / `sku`
- `spu`：`name`、`category_id`、`tags`(预留 AI：结构化标签，逗号分隔或 JSON)、`description`
- `sku`：`spu_id`、`spec`、`price`(分)、`stock`、`version`(可选乐观锁)

### 5.5 优惠券 `coupon` / `user_coupon`
- `coupon`：`type`(满减/折扣)、`threshold_amount`、`discount_amount`、`total_count`、`remain`、`start/end_time`、`per_user_limit`
- `user_coupon`：`(user_id, coupon_id)` **唯一索引**、`status`(UNUSED/USED/EXPIRED)、`used_order_id`

### 5.6 行为埋点 `user_behavior`
- `user_id`、`item_id`、`action`、`scene`、`created_at`；索引 `idx(user_id, action)`、`idx(item_id, action)`
